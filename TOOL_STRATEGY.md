# Tool Strategy Reflection

## Feature Usage Log

### 1. Interactive terminal prompt
Used for: project scaffolding and iterative verification
Why this feature: It let me run shell commands directly in the repo and confirm the environment state before editing files.
What happened: I confirmed the repository was empty and used the terminal to validate the Python environment and test setup.

### 2. /plan mode
Used for: designing the architecture for the transaction and expense modules
Why this feature: It keeps the implementation structured when there are multiple layers and rules to coordinate.
What happened: The service/repository/controller plan reduced blind generation and protected the domain boundaries.

### 3. @ file references
Used for: reviewing the generated transaction files before remediation
Why this feature: It allowed me to anchor revisions to the exact files that were already generated, rather than reworking the entire module from memory.
What happened: I targeted the generated `model.py` and `service.py` directly and replaced the unsafe implementation.

### 4. /compact
Used for: reducing context after the initial standards and module review work
Why this feature: It clears older context while preserving the project assumptions that matter to the next task.
What happened: It helped when moving from transaction remediation into expense-splitting feature work.

### 5. /clear
Used for: switching tasks between transaction remediation and expense feature implementation
Why this feature: It reduces stale assumptions from earlier prompts and keeps the next task grounded in the current architecture.
What happened: This prevented the model from carrying forward the wrong transaction assumptions into the split-expense workflow.

### 6. Model selection /model
Used for: choosing a narrower, faster model for routine scaffolding and code generation
Why this feature: It reduces cognitive drift and keeps the fast editing loop efficient while the architecture is still being shaped.
What happened: The model generally produced structurally sound code when the task was constrained to a known layered pattern.

### 7. Headless execution with direct file creation
Used for: generating the initial repository structure and baseline files
Why this feature: It is the closest match to the non-IDE workflow the project brief expects.
What happened: The project scaffolding and initial files were created quickly, which then enabled the review process.

### 8. Iterative terminal verification
Used for: validating the implementation with pytest in a compatible Python 3.12 virtual environment
Why this feature: It gave fresh evidence before completion and exposed a dependency mismatch caused by Python 3.14 compatibility.
What happened: The initial test run failed because the environment was wrong; after moving to Python 3.12, the suite passed and confirmed the fix.

## Scenario Responses

### Scenario 1: A teammate asks for a quick skeleton in a brand-new repo
Claude Code feature: Headless file generation in the terminal
Why: It is the fastest way to establish the project skeleton and file layout without polling the UI.

### Scenario 2: The repo has multiple layers and you need to keep architecture consistent
Claude Code feature: /plan
Why: It gives the model a structured implementation plan, which is essential for service/repository/controller separation.

### Scenario 3: You want to ask Claude to fix only one generated file without losing the rest of the context
Claude Code feature: @ file references
Why: This limits the model to only the relevant files and reduces context drift.

### Scenario 4: You have completed a long generation and need to keep context focused
Claude Code feature: /compact
Why: It preserves the important project rules while trimming unrelated memory and older code.

### Scenario 5: You are switching from one task to another and want a fresh context window
Claude Code feature: /clear
Why: It prevents prior assumptions from leaking into a different module or feature.

### Scenario 6: You need a faster, cheaper run for routine scaffolding
Claude Code feature: /model
Why: It lets you choose the most appropriate model for speed versus reasoning depth.

### Scenario 7: The code generation step needs direct tool execution rather than chat-only suggestions
Claude Code feature: Terminal-driven execution
Why: It creates files directly in the repo and is closest to the “generated by Claude code in the working tree” workflow described in the brief.

### Scenario 8: You want to make sure the implementation really works before completion
Claude Code feature: Iterative terminal validation
Why: Only fresh test output can confirm whether the code solves the real requirement instead of merely sounding plausible.

## Limitations Encountered

### 1. The initial environment mismatch
Prompt: “Run the project tests after setting up the Python environment.”
What went wrong: The default interpreter was Python 3.14, while the pinned Pydantic dependency chain was not compatible with it.
How detected: pytest failed with a build error in `pydantic-core`.
How fixed: I created a Python 3.12 virtual environment and reran the suite.
What I would do differently: Check the runtime compatibility before starting the dependency install step.

### 2. The first AI-generated transaction module was structurally unsafe
Prompt: “Generate a Transaction model and a Transaction service with create, get-by-user, and delete-all functions. Use a database.”
What went wrong: It produced a service-level SQLite dependency, no validation, and no repository layer.
How detected: The review compared the output against the project architecture and security standards.
How fixed: I rewrote the module into an explicit SQLAlchemy model, repository, service, and controller stack.
What I would do differently: Add a mandatory review prompt or architecture checklist after every generated module.

### 3. The first expense-splitting service overfit the obvious happy path
Prompt: “Create a SharedExpense model and a BalanceCalculationService...”
What went wrong: Custom split calculations and participant normalization were insufficiently constrained.
How detected: The tests revealed mismatched totals and inconsistent creator handling.
How fixed: I constrained the normalization and validation logic and added regression tests for equal and custom split behavior.
What I would do differently: Always generate test cases first for edge scenarios before trusting the service behavior.
